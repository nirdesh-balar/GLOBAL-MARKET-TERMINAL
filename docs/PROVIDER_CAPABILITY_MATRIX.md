# Provider capability matrix for GMT analysis

Approved routing remains public Hyperliquid market data for crypto and Yahoo Finance market data for non-crypto. Existing explicit archive imports and directory metadata remain governed by current repository policy. The installed rc.8 live-provider acceptance is prior evidence for those routes. This source audit introduces zero production subscriptions, provider changes or profile mutations.

| Capability | Yahoo Finance, non-crypto | Hyperliquid, crypto | Constraints and GMT decision |
| --- | --- | --- | --- |
| Symbols and identities | Existing catalogue/discovery; mapping and currency depend on exchange and supported listing | Public spot/perpetual identities with distinct market type and provider ID | Persist canonical IDs. Distinguish aliases, proxy instruments, redirects and delistings. |
| OHLCV and historical charts | Existing instrument and interval-specific retention, market sessions and corporate actions | Public candle snapshot and WebSocket candles; snapshot returns up to the provider's latest 5,000 candles | Preserve time zone, available range and adjustment flags. Missing bars remain gaps. |
| Streaming and time/sales | Existing route gives snapshots and potentially delayed values. No approved execution tape | Public trades carry price, size, timestamp, side and trade ID. Public candle/trade streams exist in rc.8 | Preserve connected/stale/reconnecting display, bounded reconnect and dedup. Trade side maps using published provider semantics. |
| Best bid/offer and public depth | No approved Yahoo BBO or L2 time series | Official WebSocket provides bbo and l2Book snapshots. REST public L2 exposes up to 20 levels per side | Future feature gate: verify subscription identity, depth precision, event ordering, sample rate, gaps and entire lifecycle. Treat snapshots as sampled book state. |
| Price/time liquidity view | Unavailable from approved Yahoo OHLCV | Potential from timestamped, bounded captures of public L2 | Build only coverage actually captured. Record source, sampling, depth and start/end; omit unsupported earlier periods. |
| Tape-based footprint and charts | Candle volume provides no trade-at-price distribution, aggressor direction or tick history | Exact bucketing possible only within collected trades with verified time/side and coverage | Persist analytical aggregates only if a retention design is approved. Show partial coverage and protect profiles. |
| Sweep/wall/large-print statistics | Candle-level volatility and volume metrics only | Deterministic statistics can be defined from public prints and observed depth | Express observed values and assumptions. Icebergs, absorption intent, cancel-vs-fill certainty, liquidations and hidden liquidity require verified fields and methodology. |
| Perpetual funding/open interest | Unavailable as a public crypto-perp signal here | Provider public asset context includes instrument-dependent context fields such as funding and open interest | Consider only with freshness, units and explicit coverage. Existing UI does not imply these endpoints already run. |
| Options/Greeks | Library exposes an option-chain method; product or expiry coverage and candidate NSE requirements unverified | Perpetual context is distinct from listed options | Do not promise reference option data or construct missing strikes, Greeks, quotes or depth. |
| Return map, indicators, scan and local alerts | Existing snapshots/candles, market close, freshness, and session aware | Existing candle/stream calculations with market-type context | Define denominators, time windows, stale handling, unavailable values and quantitative parity. |
| Historical public depth or trade archive | Unavailable through the approved route | Provider documents separate requester-paid archive with limited data coverage | Archive acquisition and additional paid or cloud dependencies outside current scope. |
| Executable trading signals or accounts | Out of scope | Out of scope | Keep all paths read-only with local analysis and no credentials for execution or account services. |

## Sources and validation before expanding crypto coverage

The RFC for any proposed public market-data feed should record payload samples from permitted endpoints, exchange timestamp and units, market identity, bounds and drop policy, observed cadence, retry/reconnect behavior, memory and CPU caps, and fixtures proving gap behavior. Retain a bounded stream per canonical market and share local consumers. Public REST and WebSocket quotas are external ceilings. GMT’s existing tighter limits and Grid contract apply. [WebSocket subscriptions](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions) [Public information endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint) [Rate and user limits](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits) [Provider notation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/notation) [Historical data](https://hyperliquid.gitbook.io/hyperliquid-docs/historical-data)

Yahoo limits differ by instrument and interval. Request truncation, delayed values, zero or missing volume and local market closed state are distinct. Library support for a method does not establish upstream coverage or a redistribution license. Any external distribution requires review of the applicable data terms and existing project notices.
